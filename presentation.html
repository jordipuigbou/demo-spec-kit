01
Introducción

Specification-Driven
Development

SDD es un enfoque donde los artefactos de diseño — especificación, plan y tareas — se crean antes de escribir la primera línea de código.

  • 🔴El código sin spec produce sistemas que cumplen la implementación, no el requisito
  • 🔴Tests escritos después validan lo que se hizo, no lo que se necesitaba
  • 🔴Agentes de IA sin contexto generan código plausible pero incorrecto
  • 🔴Requisitos ambiguos = retrabajo = coste exponencial
✅ CON SDD
  • ✅Los criterios de aceptación definen el contrato antes de implementar
  • ✅Los tests son trazables a requisitos concretos
  • ✅El agente de IA opera con contexto estructurado, no intuición
  • ✅QA puede intervenir desde el día 0, no en revisión
Spec → Test → Code

03
Gobernanza

La Constitución

Documento de gobernanza en .specify/memory/constitution.md que define los principios no negociables del proyecto. Todo artefacto generado se valida contra ella.

PRINCIPIO I
Test-First Development
NON-NEGOTIABLE. Tests escritos y fallando antes de cualquier implementación. Ciclo Red → Green → Refactor.
PRINCIPIO II
Testing Pyramid
Unit ≥70% · Integration 20-25% · E2E ≤10%. Umbrales de cobertura: 80% línea, 90% módulos críticos.
PRINCIPIO III
Code Quality
Zero errores en análisis estático. Complejidad ciclomática ≤10. Linting y formato sin overrides manuales.
PRINCIPIO IV
Specification-Driven
Cada test trazable a un AC. Ningún test sin requisito. Requisitos no testables son inválidos.
PRINCIPIO V
Continuous Quality Gates
CI/CD bloquea merge si falla cualquier gate. Override requiere documentación por Quality Owner.
PRINCIPIO VI
Defect Prevention
Type checking obligatorio. Security scanning en cada commit. Dependency vulnerability scanning en CI.

05
QA Integration

Dónde interviene QA

Fase Artefacto Intervención QA Valor
/speckit-specify spec.md Revisar ACs, detectar ambigüedades, validar que los escenarios son testables (Given-When-Then) Shift-left máximo
/speckit-clarify spec.md Añadir preguntas de cobertura, edge cases, flujos negativos y criterios de rendimiento Requisitos completos
/speckit-plan plan.md Verificar Constitution Check: pirámide de tests, umbrales de cobertura, herramientas de análisis estático Estrategia de test
/speckit-tasks tasks.md Confirmar que cada US tiene tareas de test, que los IDs de AC están anotados, y que los tests fallan antes de implementar Trazabilidad total
/speckit-implement código Revisar outputs de CI (JUnit XML, HTML reports), validar cobertura por US, aprobar PRs contra ACs Gate de merge
06
Customización

Override: tasks-template.md

Spec Kit permite sobrescribir cualquier template en .specify/templates/. El template de tareas ya incluye soporte para trazabilidad de ACs.

IDENTIFICADOR AC
Formato: SPXXX-USYY-CRZZ
SP010 = Sprint/Feature 010
US01 = User Story 01
CR01 = Criterion 01
REPORTE: JUnit XML + HTML
Cada ejecución de tests produce:
📄 reports/unit/junit.xml
🌐 reports/unit/html/
📄 reports/e2e/junit.xml
🌐 reports/e2e/html/
# En tasks.md (generado con override QA) - [ ] T010 [P] [US1] Vitest: card rendering AC: SP001-US01-CR01, CR02 # En el test (Vitest ≥ 4.1) it('muestra nombre y fecha del evento', async ({ annotate }) => { await annotate('acceptance-criteria', 'SP001-US01-CR01') const { getByText } = render(<EventCard {...event} />) expect(getByText('QAward Spain')).toBeInTheDocument() }) # En el JUnit XML de salida: <testcase name="muestra nombre y fecha del evento"> <properties> <property name="acceptance-criteria" value="SP001-US01-CR01"/> </properties> </testcase>
